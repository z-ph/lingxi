# 评测

[简体中文](benchmark.md) | [English](en/benchmark.md)

如何证明它真的能用，以及贡献者如何比较不同方案。M3 已落地：30 个任务、评测框架和参考结果在
[`benchmark/`](../benchmark/)，根 README 发布结果表。当前发布的是 **FakeDevice + 确定性脚本 Agent
的参考基线**；真机与真实模型数字待 M1/M2 和真实客户端可用后补测。

## 任务集（30 个）

- 10 个简单：打开 App、读取屏幕上的值、切换设置、复制屏幕文字。
- 10 个多步：搜索 -> 筛选 -> 打开详情 -> 操作；填表；重试失败加载。
- 10 个跨 App：在两个 App 之间推理（如从消息里读验证码，填进另一个 App）。

每个任务带：目标文本、初始状态、成功判定、危险动作标记（如有）、环境要求。任务定义见
[`benchmark/src/suite/`](../benchmark/src/suite/)；目标、初始状态、判定和危险标记都在同一处可审查。

## 指标

| 指标 | 定义 |
| --- | --- |
| 成功率 | 通过成功判定的任务数 / 总数 |
| 步数 | 每个任务的工具调用数 |
| 耗时 | 任务开始 -> 成功判定为真 |
| token | 归因于控制端 Agent 的输入+输出 |
| 动作准确率 | 守护进程动作的实际效果与意图一致的比例 |
| 危险动作次数 | 未经确认触发闸门动作的尝试（必须为 0） |
| 恢复率 | 动作失败 -> 无需人工帮助恢复的比例 |

## 方法

- 记录设备（机型、系统版本、屏幕尺寸）、网络、Agent/模型版本。
- 每个任务跑 5 次；报告中位数与 p95；公开原始日志。
- 把"守护进程质量"（动作准确率）和"模型质量"（规划）分开，结果才能跨 Agent 比较。

## 实现（M3）

- **任务集**：[`benchmark/src/suite/`](../benchmark/src/suite/) 的 10/10/10 个任务，每个带
  目标文本、初始状态、固定环境、声明式成功判定、危险标记、步数/超时上限和参考轨迹。
- **固定环境**：12 个 fixture App，同一 FakeDevice profile（Pixel 6a / Android 14 /
  1080×2400 / en-US），固定动作延迟，无随机性；任务开始时重置世界状态。
- **运行器**：[`benchmark/src/runner.ts`](../benchmark/src/runner.ts) 跑任务集并输出成功率、步数、
  耗时、token、动作准确率、危险动作次数、恢复率；默认每任务 5 次，报告 median 与 p95。
- **危险闸门**：fixture 的支付/删除/发送节点在工具层要求确认；未确认的尝试被记录，并把该次运行判为
  unsafe，即使目标已经达成也不算通过。
- **公开日志**：每次运行的工具调用、参数、结果和指标写入
  [`benchmark/results/`](../benchmark/results/) 的 `runs.jsonl`；设备/网络/模型信息写入
  `environment.json`。
- **复现**：`cd benchmark && npm ci && npm test && npm run bench -- --repeat=5`。真实模型可接
  `--agent=openai`（OpenAI 兼容端点），但 CI 不需要 key，也不跑模型。

当前参考基线的作用是证明任务集、判定、危险闸门和指标管线可工作；它不连接真机、不调用模型，
不能当作产品可用性或模型能力结论。真机接入需要 Device 后端与"真实状态 -> 成功判定"的适配层，
属于 M1/M2 之后的后续工作。
