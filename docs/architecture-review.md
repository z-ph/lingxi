# 架构与规范巡检

[简体中文](architecture-review.md) | [English](en/architecture-review.md)

状态：M0 定稿（issue #18）。规范见 [architecture.md](architecture.md)，机器闸机见
[ci-gates.md](ci-gates.md)。本文规定**什么时候、由谁、按什么清单**检查规范和架构是否已经漂移。

## 1. 目的

闸机只能拦截已经写进规则的问题。项目腐败通常来自规则之外：

- 文档还是 M0 的，代码已经绕出另一套边界；
- 新包、新依赖、新“临时”目录逐渐长出来；
- 同一逻辑在多个地方复制，闸机只抓到完全相同的文件；
- CI 闸机被悄悄放宽，或者 probe 早就坏了没人发现；
- milestone 验收后没有回看，留下过期假设。

定期巡检就是给这些“规则管不到、但会累积”的问题设一个固定检查点，并把发现变成有归属的 issue/PR。

## 2. 节奏

必须巡检的时机：

1. **每个月**：每月 1 日由 `.github/workflows/architecture-review.yml` 自动创建巡检 issue；有未关闭的
   巡检 issue 时不会重复创建。
2. **每个里程碑验收后**：M1、M2、M3 等验收 PR 合并后，开一次巡检，确认文档、包布局和验收结论一致。
3. **结构性变更时**：新增/删除包、修改层或依赖方向、引入新运行时依赖、改 MCP 契约或安全边界时，
   在同一个 PR 里完成架构评审记录（不一定要另开巡检 issue）。
4. **事故或回归后**：未授权访问、令牌泄露、动作静默失败、CI 连续红等事件后，检查规则缺口。

巡检 issue 的关闭不代表永久完成；下个月/下个里程碑会重新创建。

## 3. 自动提醒

`.github/workflows/architecture-review.yml`：

- `schedule`：每月 1 日 01:00 UTC；
- `workflow_dispatch`：维护者可随时手动触发；
- 以 GitHub Actions 自带 token 创建 issue，标题 `[架构巡检] YYYY-MM 规范与架构巡检`；
- 已有未关闭的 `[架构巡检]` issue 时跳过，避免刷屏；
- issue 正文链接本文并给出最小命令清单，不复制完整检查项（避免双源）。

如果自动提醒中断（Actions 被禁用、权限不足等），维护者手动按本文开 issue；不要把“没有自动 issue”
当作不需要巡检的理由。

## 4. 巡检清单

逐项给出结论；不能只写“正常”。每项要么“无需改动 + 理由”，要么链接到后续 issue/PR。

### 4.1 文档与现状

- [ ] README / README.en 的产品描述、里程碑状态与代码一致。
- [ ] [mcp-tools.md](mcp-tools.md) 的工具名、参数、错误分型与实际实现一致。
- [ ] [security.md](security.md) 的要求没有被实现静默绕过；未实现项有明确里程碑。
- [ ] [architecture.md](architecture.md) 的包表、层、`mayDependOn` 和机器契约与 `packages/` 实际一致。
- [ ] 每篇中文文档有英文镜像；英文没有孤儿；语言链接有效。
- [ ] 没有第二份机器契约、重复的规范段落或互相矛盾的默认值。
- [ ] README 文档索引包含全部主文档。

### 4.2 包布局与分层

- [ ] `packages/*` 只有登记过的包；没有根级产品源码或野生目录。
- [ ] 每个包职责单一；跨包依赖符合层号，没有循环、深导入或绕过公开入口。
- [ ] `contracts` 没有 I/O；`device` 没有 MCP/鉴权/安全策略；`daemon` 没有 Android 原生调用。
- [ ] `benchmark` 没有被产品包依赖；`tools/` 没有被产品包导入。
- [ ] 公开入口和 `exports` 清楚；内部实现没有被别的包直接引用。

### 4.3 依赖与供应链

- [ ] 新增运行时依赖已登记用途、许可证、`allowedIn`；版本在根锁文件固定。
- [ ] 没有两个依赖做同一件事；没有为一个小函数引入大库。
- [ ] 依赖仍在维护；有已知高危漏洞或长期不更新的依赖有处置计划。
- [ ] 没有提交 `node_modules/`、包级锁文件或未使用的依赖。
- [ ] 依赖许可证仍符合 architecture.md（copyleft 需人类批准）。

### 4.4 DRY 与复杂度

- [ ] 没有跨包复制粘贴；共享逻辑已下沉到允许依赖的下层或 `contracts`。
- [ ] 没有 god module：单文件承担多个职责、超过约 400 行且无说明的情况已拆分或记录。
- [ ] 重复三次以上的模式已提取；只有两处相似、会独立演化的代码没有被强行抽象。
- [ ] 错误处理、默认值、协议字段只有一份定义。
- [ ] 删除的代码没有留下死分支、过期 TODO 或“临时”开关。

### 4.5 测试与闸机

- [ ] `npm ci && npm run format:check && npm run gate && npm test && npm run build && npm run typecheck` 全绿。
- [ ] 闸机 probe 仍能在 fixture 上触发预期规则；没有因为规则改动而失效。
- [ ] 没有用 `continue-on-error`、删除步骤或缩小扫描范围绕过闸机。
- [ ] CI 时长、Node 版本矩阵和缓存仍合理；新包已被 workspace 命令覆盖。
- [ ] 行为变更都有测试；真机相关限制在 PR 中如实记录。

### 4.6 安全与边界

- [ ] 配对、令牌、局域网绑定、日志脱敏没有被新代码绕过。
- [ ] 危险动作白名单/确认/审计（M2 起）仍由 daemon 统一执行；设备层没有安全分支。
- [ ] 截图、界面树、通知等敏感数据没有进入日志、测试 fixture 或提交历史。
- [ ] 安全相关改动有 PR 中的人类明确批准。

### 4.7 未完成项与假设

- [ ] backlog、issue、PR 中没有与本规范冲突但被忽略的项。
- [ ] 文档中的“待定/假设”有负责人和触发条件；过期假设已更新。
- [ ] 上一个巡检 issue 的发现项已关闭或有明确阻塞原因。
- [ ] 当前里程碑的验收项没有因为“先合再说”被跳过。

## 5. 执行命令

在干净工作区执行：

```text
npm ci
npm run format:check
npm run gate
npm test
npm run build
npm run typecheck
```

机器可读的闸机结果：

```text
node packages/architecture-gate/src/cli.mjs --format json
```

需要统计时，可用 `git ls-files` 与 `npm ls --all` 辅助；不要把包含个人数据的截图、日志粘进 issue。

## 6. 记录与关闭

- 巡检 issue 里记录日期、执行者（人或 agent）、命令结果摘要、每项清单的结论。
- 发现分为：
  - **立即修**：安全、数据、红线违规——直接开 PR，按正常评审合并；
  - **排期修**：结构问题、债务——开有里程碑和验收的 issue，在巡检 issue 中链接；
  - **记录不改**：有明确理由的取舍——写清原因和复核条件，不能只写“暂不处理”。
- 巡检 issue 关闭前，所有发现项必须有 issue/PR 链接或“不改”的理由；否则保持打开。
- 架构变更仍按 [architecture.md](architecture.md) 第 7 节：更新机器契约、补 probe、同一 PR 完成。
- 涉及安全或产品范围的决策，由人类所有者批准；agent 不自行扩大范围。

## 7. 退出标准

一次巡检完成需同时满足：

- [ ] 第 4 节清单逐项有结论；
- [ ] 闸机与 probe 全绿，或规则缺陷已修复；
- [ ] 没有未登记的包/依赖/跨层调用；
- [ ] 每项发现都有归属（PR、issue 或明确不改理由）；
- [ ] 巡检 issue 已记录结论并关闭；
- [ ] 需要人类决策的事项已明确标注，不假装已解决。
